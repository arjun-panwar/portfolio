Linux and reliability

It didn’t crash. The kernel killed it.

1 min read

The service ran perfectly for three days. Then it disappeared. No exception, no stack trace, no error in the application logs. The container just restarted, and everything looked fine again until three days later.

It wasn’t a crash. The Linux kernel killed it.

When a container reaches its memory limit, the kernel’s OOM killer ends the process immediately. Your code never gets a chance to log anything. The only clues are an exit code of 137 and a line in the kernel log that most people never think to check.

The real cause was a slow leak. A few kilobytes per frame is invisible in a test run. At 30 frames per second, around the clock, it adds up to gigabytes in a few days. In vision pipelines the usual suspects are unbounded queues when a consumer falls behind, caches that are never trimmed, frame buffers held by references nobody released, and state kept per tracked object long after the object left the scene.

What I do on every long running inference service now:

  • Treat exit code 137 as “memory” until proven otherwise, and check the kernel log first
  • Track memory per hour for days, not just at startup. The trend matters more than the value
  • Put a hard bound on every queue, cache and buffer, with a clear policy for what gets dropped
  • Run soak tests long enough to catch slow growth before production does
