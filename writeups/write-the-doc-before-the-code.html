Write the doc before the code

1 min read

One of the most expensive sentences in engineering is “let’s just start building and figure it out.”

I’ve seen a team spend weeks building a multi camera pipeline, only to learn in the first real review that the design couldn’t handle the number of streams the product needed. The code was good. The direction was wrong. Most of it had to be rebuilt.

A two page design doc would have surfaced that in an afternoon.

As a staff engineer, writing is one of the highest leverage things I do. Not because documents are important, but because changing a paragraph is far cheaper than changing a running system.

What makes a design doc actually useful:

  • Start with the problem, not the solution. What are we solving, for whom, and what does success look like in numbers?
  • Show two or three real options with honest trade offs, including the one you didn’t pick and why
  • Call out the risks and unknowns clearly, especially hardware, scale and failure modes
  • Review it early, while it’s still cheap to change, and invite people to disagree
  • Let junior engineers write them too. Owning a design doc teaches system thinking faster than any code review

The goal isn’t paperwork. It’s making sure the whole team is building the same thing, for the same reasons, before anyone writes code.

The cheapest place to fix a design is in a doc.
