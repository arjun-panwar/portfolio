One object passed. Two alerts fired.

1 min read

One object passed through a zone. The operations dashboard showed two arrivals. The detector was right, the tracker was right, and the count was still wrong.

The bug lived between the edge and the backend.

The edge device sent the event. The backend received it and processed it. But the acknowledgment got lost on a flaky network, so the edge did exactly what it was designed to do: it retried. The backend saw a second event, treated it as new, and created a second arrival.

On unreliable networks, this isn’t an edge case. It’s normal. Any system that retries will deliver some messages more than once. The question is whether your business logic notices.

How I design CV event pipelines now:

  • Give every event a stable ID at the source, when it’s first created on the edge, and keep that same ID on every retry
  • Check the ID before acting. A short lived key store is enough to catch duplicates within the retry window
  • Make handlers safe to run twice. Setting a state is safer than incrementing a counter
  • Accept at least once delivery, and design for exactly once effect
