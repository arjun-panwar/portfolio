Networking

The network was fine. The buffer wasn’t.

1 min read

The network graphs said the link was only 30% used. Plenty of headroom. Yet several camera streams kept showing smeared frames and decoder errors.

The network wasn’t full. A buffer was.

Video traffic isn’t smooth. A camera doesn’t send a steady trickle of data. It sends each frame as a sudden burst of packets, and key frames are much bigger than the rest. When several cameras burst at the same moment, packets arrive at the receiving machine faster than the application can read them.

They wait in buffers: first the network card’s ring buffer, then the kernel’s socket receive buffer. Default sizes on most systems are tuned for ordinary traffic, not for many high bitrate streams. When a buffer fills during a burst, new packets are simply dropped. Your bandwidth graph, averaged over seconds, never shows it.

MTU makes this worse when it’s inconsistent. If one device on the path uses a different packet size than the others, you get fragmentation or silent drops that look random.

What I check on multi camera machines:

  • Receive buffer sizes, at both the socket and the network card, sized for worst case bursts rather than averages
  • MTU on every hop. Use jumbo frames only if the cameras, switches and host all agree end to end
  • Drop counters on the interface and in the kernel. They tell you exactly where packets die
  • Whether the application reads fast enough. A slow reader thread fills even a large buffer
